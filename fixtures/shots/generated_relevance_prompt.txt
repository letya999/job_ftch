We seek candidates for roles focused on engineering and integrating LLM-based production systems with strong backend development in Python. Responsibilities include building and maintaining pipelines for structured extraction, retrieval, embeddings, reranking, agent orchestration, prompt engineering with structured output, runtime guardrails, cost and latency optimization, quality evaluation (offline and human-in-the-loop), and integration of LLM APIs into real products or workflows.

We reject roles primarily focused on classical data science, product analytics, BI, or tabular ML without LLM API integration. We also reject ML research roles involving training or fine-tuning LLMs from scratch, distributed GPU training, or deep model experimentation. Exclude infrastructure-only roles centered on ML platform, MLOps, Kubernetes, or CI/CD without product-level LLM feature development.

RULES:
- A job TITLE token alone (ML/DL/NLP/Research/Engineer/Data Scientist) must NEVER by itself cause rejection - judge by the stated responsibilities.
- A team or product NAMED after a model (e.g. "команда Alice AI LLM", "Маркет AI", "GPT") does NOT make it a model-training role. Judge by what the person BUILDS, not the team name.
- ACCEPT when the responsibilities centre on USING or BUILDING WITH LLMs to ship product: building/integrating agents and agent functions, RAG/retrieval, LLM API integration, prompt engineering, structured extraction, AI automation/workflows, AI-first or "vibe-coding" fullstack, GPT/LLM product projects, or any backend/Python role whose core is shipping LLM-powered features. This holds even if the title says ML/DL/NLP Engineer and even if it sits inside a model/research-named team.
- REJECT only when the CORE is: training, fine-tuning, alignment/RLHF, or research/experimentation on models; classical data science, analytics, or BI on tabular data; data engineering / ETL; MLOps / ML-platform / infra without product LLM features; computer vision; recommender systems; or pure management with no coding.
- Tie-break: if the role both ships LLM product features AND mixes in some modelling, lean ACCEPT. If it is genuinely about creating/training the models themselves, REJECT.
- Look for LLM-API-usage signals: prompt design, structured output, retrieval/RAG, embeddings, vector search, agent orchestration, runtime guardrails, eval frameworks, cost/latency optimization, product feature development.
