# VacancyFeedback

**Слой**: `domain` + `application`
**Файлы**: `job_ftch/domain/feedback.py`, `job_ftch/application/vacancy_feedback.py`

## Что это

`VacancyFeedback` — вердикт читателя об одной опубликованной вакансии. Публикация в канал
это единственное место, где живой человек видит финальный ответ пайплайна, поэтому это же
самое дешёвое место, чтобы собрать поправку.

Это **свидетельство о границе профиля, а не решение маршрутизации**. Ни одна отметка не
меняет уже опубликованную вакансию и не влияет на текущий прогон.

## Shape

```text
VacancyFeedback
  - tenant_id
  - job_id
  - user_id
  - verdict: off_profile
  - title | url | source_name | excerpt
  - created_at
```

Identity — тройка `(tenant_id, job_id, user_id)`. Повторное нажатие того же читателя по той
же карточке это то же мнение, а не второй голос.

## Кто может отмечать

`FeedbackAudience` — три режима, выбирает владелец канала через `/feedback`:

| режим | кнопка на карточке | чью отметку принимают |
|---|---|---|
| `off` | нет | — |
| `admin` | есть | только админов |
| `all` | есть | любого читателя канала |

Публичному и закрытому каналу нужны разные ответы: открыв кнопку всем, собираешь больше
сигнала, но и шум от тех, кто не знает профиль.

Важно: карточка одинакова для всех, кто видит канал, поэтому **наличие кнопки не может
кодировать право**. Авторизация происходит в момент нажатия — `may_submit_feedback`.

Значения `"1"`/`"0"`, записанные до появления трёх режимов, читаются как `all`/`off`:
канал, уже включивший сбор, не должен молча потерять кнопку при обновлении.

## Где хранится

В run-state тенанта под ключом `bot_feedback:{tenant_id}:records`, по образцу
`publish_ledger`. Отдельная таблица не заводилась намеренно: run-state поддерживают все
бэкенды, поэтому фича не требует миграции. Журнал ограничен `_FEEDBACK_LIMIT` записями,
потому что живёт в одном значении.

Флаг включения — `bot_feedback:{tenant_id}:enabled`. Сбор опт-ин: канал без него сохраняет
прежний вид карточек.

## Агрегация

`summarize_feedback` сворачивает записи в `FeedbackSummary`:

- `total` и `distinct_jobs` — объём;
- `by_source` — по источникам, чтобы системная протечка была видна;
- `top_jobs` — `FeedbackJobTally` с числом **разных** читателей на вакансию.

## Почему перенос в негативы ручной

`promotable_texts` возвращает только тексты, набравшие порог (по умолчанию 2 разных
читателя). Дальше их переносит админ через `/negative_job`.

Автоматического переноса нет по результатам измерения 24.07.2026. Негативные шоты,
добавленные без проверки, снизили точность на принятых и уронили полноту: вакансии «не по
профилю» лежат в векторном пространстве вплотную к заявленным целевым ролям, поэтому
негатив у этой границы тянет вниз весь кластер, включая пограничные попадания.

Одно нажатие это мнение. Порог — то, что превращает его в сигнал.
