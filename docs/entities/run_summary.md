# RunSummary (Сводка запуска)

## Что это такое

`RunSummary` — это информационный объект, который
возвращается пайплайном после завершения работы (вызова
метода `pipeline.run()`).
Он содержит детальную статистику и телеметрию текущего
сеанса: сколько элементов было скачано, сколько прошло
успешно, сколько было отброшено фильтрами и сколько вызвало
ошибки.

## Зачем это нужно и ПОЧЕМУ так устроено

Когда пайплайн работает в фоне (например, через Cron или
Dagster), он абсолютно "молчит".
Вы не видите консольного вывода. `RunSummary` — это
единственный способ понять, что произошло внутри черного
ящика.

Дизайн-решение заключается в том, чтобы сделать метрики
максимально гранулярными.
Нам недостаточно знать просто "обработано 100 элементов".
Нам нужно знать, *почему* элементы не дошли до конца: они
были дубликатами, спамом, не подошли по зарплате или вызвали
`Exception` в API OpenAI. `RunSummary` аккумулирует эту
информацию и отдает её в виде удобного дата-класса.

## Как это работает изнутри (Основные поля)

Структура `RunSummary` содержит следующие ключевые поля:

### 1. Метаданные запуска
- `run_id` — Уникальный UUID конкретного запуска. Идеально для трейсинга логов.

- `tenant_id` — Идентификатор тенанта (клиента), для которого производился запуск.

- `started_at` — Временная метка старта пайплайна (в UTC).

- `finished_at` — Временная метка завершения.

### 2. Главные метрики Воронки (Funnel)
Конвейер работает как воронка: на входе много сырых данных,
на выходе — мало чистых.
- `total_fetched` — Сколько всего `RawItem` было получено от всех источников (Source).

- `total_emitted` — Сколько готовых `JobRecord` успешно достигли получателей (Sink).

- `total_dropped` — Сколько элементов было сознательно удалено узлами (Stage вернул `None` — дубликаты, спам, нерелевантное).

- `total_quarantined` — Сколько элементов заблокировал `SanitizeNode` из-за нарушения политик безопасности.

### 3. Ошибки
- `total_errors` — Важнейшая метрика. Сколько изолированных исключений (`Exception`) произошло внутри узлов.

**Важное свойство total_errors**:
В архитектуре `job_ftch` ошибки *изолированы на уровне
элемента*.
Если пайплайн обрабатывает 100 вакансий, и при обработке 5-й
вакансии OpenAI API выдал 502 Bad Gateway, пайплайн НЕ
падает.
Он логирует ошибку, увеличивает счетчик `total_errors` на 1,
и продолжает обрабатывать 6-ю вакансию.
Поэтому `total_errors > 0` не означает, что весь процесс
завершился фатальным крахом.

### 4. Детализация
- `by_source` — Словарь, разбивающий метрики выше по каждому конкретному источнику (например, сколько принес `tg_channel_A`, а сколько `career_site_B`).

- `drop_reasons` — Словарь с частотностью причин дропа. Полезно для дебага (например: `{"DedupNode": 45, "HardFilterNode": 12}`).

## Использование в коде

Обычно с результатом запуска поступают так:

```python summary = await pipeline.run(max_items=500)

# 1. Простейшая проверка: были ли новые данные?
if summary.total_emitted == 0:
    print("В источниках нет новых или релевантных вакансий.")

# 2. Мониторинг здоровья системы
# Если ошибок больше половины от успешных - что-то идет не так (упал API провайдера)
if summary.total_errors > (summary.total_emitted * 0.5):
    logger.critical(
        f"Высокий рейт ошибок! RunID: {summary.run_id}, Ошибок: {summary.total_errors}"
    )

# 3. Анализ воронки конверсии conversion = (summary.total_emitted / summary.total_fetched) * 100 if summary.total_fetched else 0 print(f"Конверсия сырых текстов в вакансии: {conversion:.1f}%")

# 4. Отправка в системы мониторинга (Prometheus, Datadog)
metrics_exporter.observe_run(summary)
```

## Типичные ошибки и что нельзя делать

1. **Путать Dropped и Errors.**

Drop (отбрасывание) — это штатное, позитивное поведение
системы.
Если фильтр отбросил 900 спамных сообщений из 1000 — это
прекрасно, пайплайн сэкономил деньги.
Ошибка (Error) — это нештатная ситуация (упала сеть, баг в
коде).

2. **Забывать логировать RunSummary в Runtime Adapters.**

Если вы пишете адаптер (например, интеграцию с RabbitMQ), вы
обязаны принять `RunSummary` после `pipeline.run()` и
залогировать его или вернуть в качестве ответа API.
Иначе вы потеряете "видимость" (observability) работы
системы.

3. **Игнорировать метрики by_source.**

Часто `total_errors` может быть равно 10, и кажется, что всё
в порядке.
Но анализ `by_source` покажет, что один конкретный карьерный
сайт выдает 100% ошибок из-за изменившейся верстки, в то
время как Telegram-каналы работают штатно.
