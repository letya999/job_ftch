## Part 0: Pre-flight — Audit Bug Fixes (MUST land first, before any phase 17+ code)

### Fix 0.1 [CRITICAL] — Failing test: test_phase16_e2e.py

**File**: `tests/test_phase16_e2e.py`
**Problem**: `test_phase16_sqlite_persistence_restart_search` asserts `db_file.exists()` after `run_pipeline`.
The test uses `llm_backend` defaulting to `"heuristic"`. With heuristic extraction on
`fixtures/e2e/multisource_positive.jsonl`, all items are dropped before `JobAggregationNode`
(heuristic LLM cannot reliably extract valid Jobs from the fixture), so the SQLite file
is never created. The test is incorrectly designed.

**Fix**: Rework the test so that:
1. It either directly calls `SQLiteJobBackend.save(job)` with a handcrafted Job (no pipeline),
   verifying persistence and restart semantics without depending on LLM extraction; OR
2. Wraps extraction in a minimal pipeline that stubs extraction (saves Job directly).
The test should verify: file created → data persisted → new instance → search returns results.
Do NOT change the production code for this fix — only the test.

### Fix 0.2 [HIGH] — `delete()` uses wrong identity key — data corruption

**Files**: `domain/job_group.py`, `infrastructure/backends/jobs/sqlite.py`, `infrastructure/backends/jobs/postgres.py`

**Problem**: `remove_job_from_group(group, job_id)` at `domain/job_group.py:262` filters by
`j.raw_item_id != job_id`. But both backends call `delete(job.stable_id)` where the argument
is the DB primary key (`jf_jobs.job_id = stable_id`). Since `stable_id != raw_item_id`,
`remove_job_from_group` never matches any job, so `JobGroup.jobs` never shrinks.
Result: deleted jobs remain in the persisted JSON blob, `source_count` stays inflated,
URL/fingerprint indexes are re-persisted with stale data. This is data corruption.

**Fix**: Change `domain/job_group.py::remove_job_from_group` to filter by `stable_id`:
```python
new_jobs = [j for j in group.jobs if j.stable_id != job_id]
```
The `job_id` parameter name is unchanged; callers already pass `stable_id`. The domain
helper just needs to compare the right field.

Add backend-level test in `tests/test_phase16_sqlite_job_backend.py`:
- Save two jobs that land in one group (same company + title → same fingerprint or same URL)
- Call `delete(job.stable_id)` on one
- Assert `get_group().source_count == 1`
- Assert `find_by_fingerprint(...)` no longer returns the deleted job's stale group
- Assert `get_job(deleted_id)` returns None

### Fix 0.3 [MEDIUM] — `HybridSearchBackend` missing `close()` — connection leak

**File**: `infrastructure/backends/search/hybrid.py`

**Problem**: `HybridSearchBackend` creates an owned `fts_backend` (SQLiteJobBackend or
PostgreSQLJobBackend) and optionally a `vector_backend`, but has no `close()` method.
`app.run_search` calls `getattr(search_backend, "close", None)` — which is `None` for
hybrid, so the underlying connections are never closed. The test in
`test_phase16_hybrid_search.py` works around this by calling `backend.fts_backend.close()`
directly, which is a red flag.

**Fix**: Add `async def close(self) -> None` to `HybridSearchBackend`:
```python
async def close(self) -> None:
    for component in (self.fts_backend, self.vector_backend):
        close_fn = getattr(component, "close", None)
        if callable(close_fn):
            await close_fn()
```
Update `test_phase16_hybrid_search.py` to use `backend.close()` instead of
`backend.fts_backend.close()`.

### Fix 0.4 [LOW] — `WorkMode.UNKNOWN` wrong case comparison in search_text

**File**: `application/search_text.py`

**Problem**: Line contains `str(job.work_mode) != "UNKNOWN"`. `WorkMode` is a `StrEnum`
with value `"unknown"` (lowercase). So `str(job.work_mode)` yields `"unknown"`, and the
comparison `!= "UNKNOWN"` is always True, meaning `"unknown"` gets appended to embedding
text for every job that has no work mode.

**Fix**: Change to `job.work_mode != WorkMode.UNKNOWN` (import `WorkMode` from domain if not
already imported). Add unit test in `test_phase16_job_group_helpers.py` or a new
`test_search_text.py`: job with `work_mode=WorkMode.UNKNOWN` → `build_job_embedding_text`
does not contain `"unknown"`.

### Fix 0.5 [LOW] — `applied_profile=None` misleads when default profile is active

**File**: `app.py` (around line 344-345)

**Problem**: `summary.applied_profile` is only set when a custom `filter_profile_path` is
configured. When no path is given, the pipeline still applies `FilterProfile.default()`,
but `applied_profile` stays `None`. This makes the RunSummary claim no profile was active,
which is false.

**Fix**: Change the wiring in `app.py::run_pipeline` so that `applied_profile` is always
populated — either the name of the custom profile, or `"default"` when no custom path is
given. No changes to `Pipeline` or `RunSummary` structure needed.

### RM-087 — Asyncio scheduler
`application/scheduler.py` — `Scheduler` class:
```python
class Scheduler:
    def __init__(
        self,
        settings: Settings,
        run_fn: Callable[[Settings], Awaitable[RunSummary]],
    ) -> None: ...

    async def run_forever(self) -> None:
        """Loop: run pipeline, sleep interval, repeat. Handles SIGINT/SIGTERM."""
```
Pure asyncio — no Celery, no APScheduler. One `asyncio.sleep` per interval.
Handles `SIGINT`/`SIGTERM` via `asyncio.Event`: sets a stop event, drains the in-flight
run, then exits cleanly.
Per-source interval override: if any source in `settings` has `interval_seconds`, use the
minimum across all sources as the effective interval. Fall back to
`settings.schedule_interval_seconds`. Fall back to 3600 if neither is set.

### RM-088 — Daemon CLI mode
Add `--daemon` flag to the `pipeline` subcommand in `app.py::parse_args`.
When `--daemon` is set: call `Scheduler.run_forever()` instead of single `pipeline.run`.
Write PID file to `{JOB_FTCH_RUN_DIR}/.pid` on startup; delete on exit.
`JOB_FTCH_RUN_DIR` defaults to `.runtime/`.

### RM-089 — Rate-limit and backoff policy
Add to `SourceSpec` (all variants, as optional fields with sensible defaults):
```python
rate_limit_min_interval_seconds: float = 0.0
rate_limit_backoff_multiplier: float = 2.0
```
`Scheduler` enforces `rate_limit_min_interval_seconds` before each source dispatch.
This prevents TG flood-wait and HTTP 429 on repeated runs.

### RM-090 — Scheduler observability
`RunSummary` gains two new fields (additive, no breaking change):
```python
scheduled_run_index: int = 0   # 0 = single run, N = N-th daemon run
source_run_id: str | None = None
```
`--status` CLI flag: reads last run from store (`get_run_state("pipeline.status")` +
`get_run_state("pipeline.finished_at")`) and prints to stdout.

## Notes for Implementer

- Python 3.12+, asyncio, pydantic v2, mypy strict. No `# type: ignore` without a comment explaining why.
- `domain/` imports ONLY pydantic + stdlib. ZERO exceptions.
- `application/` imports ONLY `domain/` + stdlib + pydantic.
- `nodes/`, `sinks/` import ONLY `domain/` + `application/`.
- `infrastructure/` can import anything.
- All new external libs must be added to `docs/tech_stack.md` first.
- All new source/sink/store backends self-register via `@register_*` decorator — no `if/elif` dispatch in core.
- Sinks must NOT rewrite whole files on each emit.
- No credentials in any source spec or YAML. Only via `AuthProvider`.
- feedparser, websockets, aiohttp must be in extras groups `[feeds]`, `[realtime]` — NOT in core deps.
