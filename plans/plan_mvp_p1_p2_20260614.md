## BLOCK 2 — Default store → Postgres with fail-fast on missing DSN

### What the user wants

Postgres is the production store. If `store_backend = "postgres"` and `store_dsn` is not set → **raise a clear startup error**, do not silently fall back. SQLite stays available but is not the default.

### Changes

**File: `job_ftch/config.py`**

Change line 21:
```python
# BEFORE:
store_backend: str = "memory"
# AFTER:
store_backend: str = "postgres"
```

Add a `@model_validator(mode="after")` (or add to existing validators) that raises `ValueError` if `store_backend == "postgres"` and `store_dsn` is None or empty:
```python
if self.store_backend == "postgres" and not self.store_dsn:
    raise ValueError(
        "store_backend='postgres' requires STORE_DSN env var to be set. "
        "Example: STORE_DSN='postgresql+asyncpg://user:pass@host:5432/dbname'. "
        "Set store_backend='sqlite' or 'memory' to run without Postgres."
    )
```
Place this validator after the existing `normalize_backend_keys` validator (around line 139).

**File: `job_ftch/domain/tenant.py`**

Change line 83:
```python
# BEFORE:
store_backend: str = "memory"
# AFTER:
store_backend: str = "postgres"
```

**File: `job_ftch/infrastructure/stores/__init__.py`** (or wherever `create_store_with_fallback` is defined)

Find `create_store_with_fallback`. Remove or gate the sqlite/memory fallback so that if `settings.store_backend == "postgres"` and connection fails at startup, it raises instead of silently degrading. Keep the fallback only for `store_backend != "postgres"`.

**Tests:**

- Add test: `Settings(store_backend="postgres", store_dsn=None)` → raises `ValueError` with message containing `STORE_DSN`.
- Add test: `Settings(store_backend="postgres", store_dsn="postgresql+asyncpg://...")` → validates OK.
- Existing tests that use `InMemoryStore` directly are unaffected — they don't go through `Settings` defaults.
- For tests that instantiate `Settings()` without args: add `store_dsn="postgresql+asyncpg://test"` or set `store_backend="memory"` in those fixtures. Search for `Settings()` in `tests/` and patch.

**Commit:** `feat(store): default store_backend=postgres; fail-fast if STORE_DSN not set`

## BLOCK 4 — Resume file upload → CandidateProfile

### What the user wants

Send a PDF/DOCX/TXT file to the bot → bot extracts structured `CandidateProfile` via heuristics → saves and activates it. No LLM required for MVP.

### Changes

**File: `job_ftch/adapters/telegram_bot/bot.py`**

In `handle_update()`, after the existing `text = message.get("text")` block, add document handling BEFORE the `if not isinstance(text, str): return` check:

```python
document = message.get("document")
if document and not isinstance(text, str):
    await self._handle_resume_document(document, chat_id=chat_id, user_id=user_id)
    return
```

Add new method `async def _handle_resume_document(self, document: dict, *, chat_id: int, user_id: int) -> None`:
1. Get tenant_id: use the first tenant in `self._runner.tenant_ids()` or read from store `"config:active_tenant:{user_id}"`. For MVP, use first available tenant.
2. Download file bytes: call Telegram Bot API `getFile` then download via HTTP. Use `self._sender` or a new `_download_file(file_id: str) -> bytes` helper.
3. Extract text from bytes based on `document["mime_type"]` or file name extension:
   - `text/plain` or `.txt`: `content.decode("utf-8", errors="replace")`
   - `application/pdf` or `.pdf`: use `pypdf.PdfReader` (import inside try/except with user-friendly error if not installed)
   - `application/vnd.openxmlformats-officedocument.wordprocessingml.document` or `.docx`: use `docx.Document` from `python-docx`
4. Call `build_profile_from_resume_text(text, user_id=str(user_id))` (new function below)
5. Save: `await self._runner.save_candidate_profile(tenant_id, managed_profile)`
6. Activate: `await self._runner.set_active_candidate_profile(tenant_id, str(user_id), managed_profile.profile_id)`
7. Reply: `"✓ Profile created from resume.\nProfile ID: {profile_id}\nRoles detected: {roles}\nSkills detected: {skills[:5]}"`

**File: `job_ftch/adapters/profile_inputs.py`**

Add new function `build_profile_from_resume_text(text: str, *, user_id: str, profile_id: str | None = None) -> ManagedCandidateProfile`:

Heuristic extraction (no LLM, no external API):
- `profile_id`: auto-generate as `f"resume_{datetime.now().strftime('%Y%m%d_%H%M%S')}"` if not provided
- `name`: first non-empty line of text, stripped, max 100 chars
- `summary`: first 400 chars of text
- `target_roles`: scan text for role keywords (case-insensitive): `["engineer", "analyst", "developer", "manager", "lead", "architect", "scientist", "designer", "researcher", "specialist", "consultant", "devops", "mlops", "dba", "qa", "tester"]`. Collect surrounding context (2 words before + keyword). Deduplicate. Max 10 items.
- `required_skills`: scan for known tech terms: `["python", "sql", "java", "go", "typescript", "javascript", "react", "postgres", "postgresql", "mysql", "mongodb", "redis", "kubernetes", "k8s", "docker", "spark", "dbt", "kafka", "airflow", "dagster", "prefect", "tensorflow", "pytorch", "scikit-learn", "pandas", "numpy", "fastapi", "django", "flask", "celery", "rabbitmq", "elasticsearch", "clickhouse", "bigquery", "snowflake", "databricks", "aws", "gcp", "azure", "terraform", "ansible"]`. Return as `tuple[SkillTag, ...]` using `SkillTag(canonical_name=term)`.
- `relevance_threshold`: `0.3` (permissive default)
- Build `CandidateResumeSnapshot(raw_text=text[:5000])` and attach to profile
- Return `ManagedCandidateProfile(user_id=user_id, profile_id=profile_id, profile=candidate_profile, updated_at=datetime.now(UTC))`

Use existing imports: `CandidateProfile`, `CandidateResumeSnapshot`, `ManagedCandidateProfile`, `SkillTag` from `job_ftch.domain`.

**File: `pyproject.toml`**

Add optional extras group (do NOT add to core dependencies):
```toml
[project.optional-dependencies]
resume = ["pypdf>=4.0", "python-docx>=1.1"]
```

**New test file: `tests/test_profile_from_resume.py`**

Test `build_profile_from_resume_text` with a hardcoded sample resume string. Assert:
- Returns `ManagedCandidateProfile`
- `profile_id` is set
- `profile.required_skills` contains expected skills found in sample
- `profile.resume.raw_text` is non-empty

**Commit:** `feat(bot): resume file upload → CandidateProfile via heuristic extraction`

## BLOCK 5 — Bulk source add `/addsources`

### What the user wants

Paste a multiline list of URLs / `@channels` in one bot message → all added at once.

### Changes

**File: `job_ftch/adapters/telegram_bot/bot.py`**

Add command `/addsources <tenant_id>` in `handle_command()`:

Parsing: `args[0]` = tenant_id. Remaining part of `arg_text` after the tenant_id = newline-separated source links.
```
/addsources my_tenant
https://hh.ru/employer/123
@ai_jobs_ru
@data_jobs_kz
https://karriera.kz/vacancies
```

Implementation:
1. Split remaining text by newlines, strip each, filter empty strings.
2. For each link: call `build_source_spec_from_input(link, auth_provider=...)` then `runner.add_source_spec(tenant_id, spec, added_via="telegram_bot", added_by=str(user_id), input_value=link)`.
3. Collect successes and failures (catch exceptions per-item, don't abort whole batch).
4. Reply summary: `"Added {ok}/{total} sources.\nFailed:\n{failures_list}"` or `"All {ok} sources added."` if no failures.
5. Add to bot help text in `/start`.

**New test file: `tests/test_bot_addsources.py`**

Mock `runner.add_source_spec` and `build_source_spec_from_input`. Verify called correct number of times with correct links. Test partial-failure case.

**Commit:** `feat(bot): /addsources command for bulk source registration`

## BLOCK 6 — Notification mode: immediate vs digest

### What the user wants

Per-tenant switch: notify per job immediately OR batch into a digest at end of run.

### Changes

**File: `job_ftch/adapters/telegram_bot/bot.py`**

Add command `/setnotify <tenant_id> <mode>` where mode is:
- `immediate` — post each job as it is emitted (existing behaviour via TelegramPostingSink)
- `digest` — buffer all jobs from the run, send one digest message at the end

Implementation:
- Save to store: `await runtime.store.set_run_state("config:notify_mode", mode)`
- For `digest` mode save batch size if provided: `/setnotify my_tenant digest 10`
- Reply: `"Notification mode set to {mode} for {tenant_id}."`

**File: `job_ftch/application/tenant_runner.py`**

In `run_tenant()`, after the pipeline run completes (`summary = await builder.run_async(...)`):
1. Read `notify_mode = await runtime.store.get_run_state("config:notify_mode")` (default `"immediate"`)
2. If `notify_mode == "digest"` and `summary.emitted > 0`:
   - Collect emitted `JobRecord` objects from summary (or re-query from job backend, whichever is simpler)
   - Format via `format_job_digest(jobs)` from `job_ftch.adapters.telegram_bot.formatter`
   - Send via TelegramBotSender if available (inject or pass as optional callback to TenantRunner)
   - This is MVP: simplest working version, not perfect

For MVP, if injecting TelegramBotSender into TenantRunner is complex, alternative: store emitted jobs in `RunSummary` and let the FastAPI webhook handler send the digest after `run_tenant()` returns. Pick whichever is simpler given current code structure.

**Commit:** `feat(bot): /setnotify command for immediate vs digest notification mode`
