## PHASE 23 — Multi-tenant and multi-instance (RM-115 .. RM-120)

### RM-115 TenantConfig model — `job_ftch/domain/tenant.py` (NEW)
- `OutputSpec(BaseModel)`: `backend: str = "json_file"`, `path: Path | None`, `table: str | None`, `format: str = "json"` (unifies sink backend + path/table + format).
- `ScheduleSpec(BaseModel)`: `interval_seconds: int | None = Field(default=None, gt=0)`, `ingest_mode: str = "polling"`.
- `TenantConfig(BaseModel)`: `tenant_id: str` (slug, validate `^[a-z0-9_-]+$`), `display_name: str`, `sources: list[SourceSpec]`, `output: OutputSpec`, `schedule: ScheduleSpec | None = None`, `auth_provider: str | None = None`, `filter_profile_path: Path | None = None`.
- domain-only imports (pydantic + `job_ftch.domain.source_spec.SourceSpec`). NO application/infra imports.
- Export from `job_ftch/domain/__init__.py`: `TenantConfig`, `OutputSpec`, `ScheduleSpec`.

### RM-116 Tenant config loader — `job_ftch/application/tenant_loader.py` (NEW)
- `load_tenants(configs_dir: Path) -> list[TenantConfig]`: scan `*.yaml`/`*.yml`/`*.json`, validate each against `TenantConfig`.
- Support single-file multi-tenant format: a file with top-level `tenants:` list → expand to N `TenantConfig`.
- Reject duplicate `tenant_id` across files with a clear `ValueError`.
- Add `configs_dir: Path | None = None` to `Settings` (`job_ftch/config.py`); CLI `--configs-dir` flag in `job_ftch/cli.py`.
- Reuse existing YAML loader pattern from `application/source_loader.py` (match its parsing/error style).

### RM-117 Tenant-isolated store and sink namespacing
- Store keys prefixed with `{tenant_id}:` ON TOP of existing `{source_kind}:{source_name}:` namespacing (extends RM-066).
  - Add optional `tenant_id: str | None = None` parameter threaded into the `Store` run-state key builder. Implement in `infrastructure/stores/in_memory.py`, `sql_adapter.py` (so sqlite+postgres inherit). Keep default `None` → no prefix (back-compat; all existing tests pass unchanged).
- `JsonFileSink` and Postgres job/store paths/schemas interpolate `{tenant_id}` when present.
- `RunSummary` (`application/pipeline.py`): add `tenant_id: str | None = None` field; include in `as_dict()` and logs.

### RM-118 Multi-tenant pipeline runner — `job_ftch/application/tenant_runner.py` (NEW)
- `TenantRunner`: builds one `Pipeline` + `CompositeSource` per `TenantConfig` via `PipelineBuilder` (translate `TenantConfig` → builder calls; reuse `BuildProfile`/`to_settings` plumbing where helpful but driven by tenant fields and tenant_id).
- `async run_one(tenant: TenantConfig) -> RunSummary` — stamps `RunSummary.tenant_id`.
- `async run_all(tenants: list[TenantConfig], concurrency: int = 4) -> list[RunSummary]` — `asyncio` fan-out with a bounded semaphore; one tenant failing is isolated (caught, logged, returns a failed `RunSummary`), never cancels others.
- Wire `Scheduler` (`application/scheduler.py`) to accept per-tenant interval from `TenantConfig.schedule`.

### RM-119 Multi-instance isolation contract
- Document + test: two `TenantRunner` instances over the same `configs_dir` must not corrupt each other's store.
- Postgres relies on MVCC; pool serialises writes. SQLite: ensure WAL mode / per-tenant key isolation prevents cross-talk.
- Integration test: two runners, same tenant, concurrent → no duplicate output items, no store corruption.

### RM-120 Tenant management CLI — extend `job_ftch/cli.py`
- `job_ftch tenants list` — tenant IDs, display names, source counts.
- `job_ftch tenants status <tenant_id>` — last `RunSummary` from store.
- `job_ftch tenants run <tenant_id>` — single-tenant run (bypasses Scheduler).
- `job_ftch tenants reset <tenant_id>` — clear store namespace for that tenant (add `Store`/`StoreConnector` helper to delete by `{tenant_id}:` prefix).

### Phase 23 tests (`tests/`)

- `test_tenant_loader.py`: multi-file dir load, single-file `tenants:` format, duplicate id rejection.

## PHASE 24 — FastMCP server (RM-121 .. RM-127)

Build a full server under `job_ftch/adapters/mcp/` (package). The existing flat `adapters/mcp_adapter.py` stays as the low-level `create_mcp_server(builder, ...)` building block; the new server composes tenants on top.

### RM-121 FastMCP server core — `job_ftch/adapters/mcp/server.py` (NEW)
- `create_server(configs_dir: Path, *, search_backend: SearchBackend | None = None, token: str | None = None) -> FastMCP`.
- Guard `from fastmcp import FastMCP` with try/except → ImportError "pip install job-ftch[mcp]".
- Lifecycle: startup loads tenants via `load_tenants`, builds `TenantRunner`, starts `Scheduler` as a background task; shutdown drains in-flight pipelines, flushes sinks, closes store connections.
- Transports: stdio (default) and SSE/HTTP. Optional Bearer token from env `JOB_FTCH_MCP_TOKEN` (param `token` overrides).

### RM-122 MCP tools surface (register on the server)
- `run_pipeline(tenant_id: str) -> dict` — immediate ingest for one tenant (`TenantRunner.run_one`).
- `run_all_pipelines() -> list[dict]` — all tenants in parallel (`run_all`).
- `get_status(tenant_id: str) -> dict` — last `RunSummary` from store.
- `list_tenants() -> list[dict]` — loaded tenants + last-run metadata (`TenantInfo`).
- `search_jobs(query: str, tenant_id: str | None = None, limit: int = 20) -> list[dict]` — delegates to `SearchBackend`; `tenant_id=None` → across all tenants. Returns `JobGroup.model_dump(mode="json")`.
- `get_job(job_id: str) -> dict` — single job via `JobPersistenceBackend.get_job`.
- `reset_tenant(tenant_id: str) -> dict` — clear dedup store for a tenant (admin).

### RM-123 MCP resources surface
- `jobs://{tenant_id}/latest` — last N extracted jobs as JSON array.
- `jobs://{tenant_id}/run_summary` — last `RunSummary` resource.
- `config://{tenant_id}` — sanitised `TenantConfig` (strip any auth refs; never expose secrets).
- Resources read-only; mutations only via tools.

### RM-124 Client compatibility + RM-126 plugin packaging
- Add `job_ftch mcp-server` CLI command to `cli.py`: auto-detect transport (stdio default; `--transport sse --host --port`).
- Entry point in pyproject.toml: `[project.entry-points."job_ftch.mcp_servers"] default = "job_ftch.adapters.mcp.server:create_server"`.
- `[mcp]` extras already has `fastmcp`; add `uvicorn` to `[mcp]` for SSE (already in `[api]`/`[all]` — add to `[mcp]` too).

### RM-128 FastAPI webhook bridge — `adapters/telegram_bot/api.py`
- FastAPI app. Endpoints:
  - `POST /webhook/telegram` — validate `X-Telegram-Bot-Api-Secret-Token` header against configured secret (via AuthProvider/env), feed update to bot dispatcher.

  - `GET /jobs/search?q=&tenant_id=&limit=` — delegate to `SearchBackend`.
- FastAPI lifespan: startup builds `TenantRunner`; shutdown drains pipelines.
- Auth: Telegram secret token + optional internal API key. All via `AuthProvider`, never hardcoded.

### RM-129 Telegram bot handler — `adapters/telegram_bot/bot.py`

- Inline keyboards: job cards with Details / Open URL / Next page (callback queries).
- Per-user command throttle (simple in-memory rate limiter).

### RM-130 Job digest formatter — `adapters/telegram_bot/formatter.py`
